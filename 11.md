Admin Job Configuration Page — Technical Design

Status: Draft for reviewOwner: Boyi ZhaoReviewer: JianRepositories: recruitdirect-web, webserviceDate: 2026-07-26

1. Background

RecruitDirect currently stores job information in the Java Job entity and exposes job-management APIs under /job. The frontend console uses Vue 3, Pinia, Vue Router, Vuetify, Firebase Authentication, and Axios. The backend uses Spring Boot, Spring MVC, Spring Data JPA, and MySQL.

The requested feature is an administrator-only page where an admin can:

Enter a Job ID.

Load the corresponding job information.

Load four job-level configuration values:

Resume process limit

Interview limit

Resume process model

Interview model

Edit the configuration.

Save the updated configuration to the database.

This document describes the proposed frontend, API, authorization, backend, and database changes. Development will begin after this design is approved.

2. Goals

The implementation will:

Add a new Job Configuration entry to the console left sidebar.

Show the sidebar entry only to console users whose HiringClient.role is admin.

Add a protected route for the page.

Prevent non-admin users from opening the page directly by URL.

Allow an admin to load a job by its existing Job UUID.

Display a small set of read-only job information for verification.

Display and edit the four requested configuration fields.

Validate the input in both the frontend and backend.

Save the values atomically to the existing job table.

Enforce admin authorization on the backend, independently of frontend visibility.

Preserve compatibility with existing jobs and existing Job APIs.

3. Non-goals

The following items are not included unless separately approved:

Changing the existing job-posting or job-editing page.

Allowing normal hiring clients or recruiters to modify these settings.

Supporting bulk updates for multiple jobs.

Adding configuration history or rollback.

Adding a global configuration page.

Changing the Firebase login flow.

Replacing the existing Axios authentication interceptor.

Wiring the four values into resume-processing, interview-processing, Python automateservice, SQS workers, or OpenAI model execution. This design stores and manages the values. Runtime consumption must be confirmed separately.

Supporting lookup by short_id. The initial design uses the existing full Job UUID because current Job APIs already use that identifier.

4. Existing Architecture Relevant to This Change

4.1 Frontend authentication and user role

Firebase login information and the Firebase ID token are managed in:

src/stores/auth.ts

RecruitDirect business-user information is loaded from the Java backend and stored in:

src/stores/authUser.ts

The business-user object contains the role used by the console frontend. Current admin visibility checks use:

usersStore.userData.role === 'admin'

Axios requests automatically include:

Authorization: Bearer <firebase-id-token>

through the existing Axios interceptor.

4.2 Frontend sidebar

Sidebar items are defined in:

src/layouts/full/vertical-sidebar/sidebarItem.ts

The menu type already supports:

requiresAdmin?: boolean

VerticalSidebar.vue filters admin-only items based on usersStore.userData.role.

4.3 Frontend routing

Console routes are registered in:

src/router/MainRoutes.ts

The global navigation guard is implemented in:

src/router/index.ts

The existing guard checks console authentication and customer organization-admin access. It does not currently enforce a console HiringClient.role === 'admin' route requirement.

4.4 Frontend Job API access

Job-related state and HTTP calls are managed in:

src/stores/jobList.ts

The existing store already supports loading a job using:

GET /job/info?jobId={jobId}

The new configuration page will follow the same Axios and Pinia patterns.

4.5 Backend Job architecture

The existing backend flow is:

JobController
    -> JobService
        -> JobRepository
            -> Job entity / job table

Relevant existing files:

recruitdirect-service/.../controller/JobController.java

recruitdirect-domain/.../service/JobService.java

recruitdirect-domain/.../repository/JobRepository.java

recruitdirect-domain/.../model/entity/Job.java

Job maps to the MySQL job table. Its primary key is stored as byte[] in Java and exposed as a UUID string through getId() and setId(String).

The entity already contains several job-scoped operational settings, including interview language, follow-up enablement, interview expiration date, resume-required status, and email template. Therefore, the four new settings fit the existing Job aggregate.

4.6 Backend authentication

Protected endpoints use:

@RequireAuth

FirebaseAuthInterceptor validates the Authorization header through FirebaseService.

Existing code also contains a console-admin role:

HiringClient.Role.admin

An existing controller already demonstrates explicit admin checking. Therefore, @RequireAuth will be used for authentication, followed by a separate HiringClient.Role.admin authorization check.

5.3 Page states

The page will explicitly handle:

Initial state: no job loaded.

Loading state: disable lookup and show progress.

Job not found: show a clear 404 message.

Unauthorized: redirect or show access denied.

Configuration loaded: display the form.

Dirty state: indicate unsaved changes.

Saving state: disable form and show progress.

Save success: show snackbar or alert.

Save failure: preserve edited values and show the backend error.

Reset: restore the last successfully loaded values.

7. API Design

7.1 Get job configuration

GET /job/admin/configuration/{jobId}
Authorization: Bearer <firebase-id-token>

Authorization

@RequireAuth

Console Firebase realm

Current HiringClient.role must equal admin

Success response — 200 OK

{
  "job": {
    "id": "0b36f5dc-0cf3-4bb2-81de-c7fa2ee03d76",
    "shortId": "00042",
    "title": "Software Engineer",
    "companyId": 12,
    "companyName": "Example Company",
    "jobStatus": "ACTIVE"
  },
  "configuration": {
    "resumeProcessLimit": 50,
    "interviewLimit": 20,
    "resumeProcessModel": "gpt-4.1-mini",
    "interviewModel": "gpt-4.1"
  }
}

For legacy jobs, unconfigured values may be null.

Error responses

Status

Condition

400

Job ID is blank or malformed

401

Missing, invalid, or expired Firebase token

403

Authenticated HiringClient is not an admin

404

Job does not exist

500

Unexpected server error

7.2 Update job configuration

PUT /job/admin/configuration/{jobId}
Authorization: Bearer <firebase-id-token>
Content-Type: application/json

Request body

{
  "resumeProcessLimit": 50,
  "interviewLimit": 20,
  "resumeProcessModel": "gpt-4.1-mini",
  "interviewModel": "gpt-4.1"
}

Validation

resumeProcessLimit

null or a positive integer.

interviewLimit

null or a positive integer.

resumeProcessModel

null or a trimmed non-empty string.

Maximum recommended length: 128 characters.

interviewModel

null or a trimmed non-empty string.

Maximum recommended length: 128 characters.

Empty strings are normalized to null.

The exact business maximum for the two limits must be confirmed. The initial backend validation should enforce positivity without inventing an unsupported upper limit.

Success response — 200 OK

Return the same response shape as the GET endpoint, containing the persisted values.

Error responses

The update endpoint uses the same 400/401/403/404/500 behavior as the GET endpoint.

7.3 Why use a dedicated configuration API

The current /job/update/info endpoint updates many normal job-posting fields. The new configuration is admin-only and has a different authorization policy. A dedicated API avoids:

Exposing admin fields through the normal job-edit flow.

Expanding an already large update payload.

Allowing normal hiring clients to modify system-processing settings.

Coupling configuration changes to job-description changes.

Accidentally regenerating interview or resume criteria.

8. Backend Design

8.1 Controller

Modify:

recruitdirect-service/src/main/java/com/recruitdirect/controller/JobController.java

Add two protected endpoints:

@RequireAuth
@GetMapping("/admin/configuration/{jobId}")

@RequireAuth
@PutMapping("/admin/configuration/{jobId}")

Responsibilities:

Obtain the authenticated Firebase identity from the existing request context.

Resolve the corresponding console HiringClient.

Enforce HiringClient.Role.admin.

Validate the path and request body.

Call JobService.

Map the Job entity into an admin configuration response DTO.

Return appropriate HTTP status codes.

8.2 Admin authorization

Authentication and authorization are separate:

@RequireAuth
    -> verifies the Firebase ID token
    -> identifies the authenticated user

Admin role check
    -> resolves HiringClient
    -> requires HiringClient.Role.admin

Recommended implementation:

Add a reusable requireAdmin(...) method to HiringClientService, or use the same lookup and role-check pattern already used by existing console controllers.

Do not trust the frontend localStorage.role.

Do not accept an admin email or role from the request body.

Return 403 Forbidden for a valid non-admin user.

If the existing global exception handler does not cover a suitable console access-denied exception, add a small AdminAccessDeniedException and map it to 403.

8.3 Request and response DTOs

Create:

recruitdirect-service/src/main/java/com/recruitdirect/model/AdminJobConfigurationUpdateRequest.java

Proposed fields:

private Integer resumeProcessLimit;
private Integer interviewLimit;
private String resumeProcessModel;
private String interviewModel;

Create:

recruitdirect-service/src/main/java/com/recruitdirect/model/AdminJobConfigurationResponse.java

It should contain:

Minimal read-only job summary.

The four configuration values.

DTOs prevent direct exposure of the full JPA entity and keep the admin API stable if the entity changes.

8.4 Service

Modify:

recruitdirect-domain/src/main/java/com/recruitdirect/service/JobService.java

Add:

@Transactional(readOnly = true)
public Job getJobConfiguration(String jobId)

@Transactional
public Job updateJobConfiguration(
    String jobId,
    Integer resumeProcessLimit,
    Integer interviewLimit,
    String resumeProcessModel,
    String interviewModel
)

Recommended implementation:

Convert the UUID string to bytes using UTF-8, consistent with current code.

Use inherited jobRepository.findById(...).

Throw a not-found exception if absent.

Validate and normalize the four values.

Set the fields on the entity.

Update modifiedAt.

Call jobRepository.save(job).

Return the saved entity.

Using findById is preferable to getReferenceById for this admin API because it provides a clear 404 path instead of a delayed proxy failure.

8.5 Repository

No new custom Repository query is required for the initial implementation.

JobRepository already extends:

JpaRepository<Job, byte[]>

Therefore, inherited findById and save are sufficient.

A custom native UPDATE query may be added later only if performance or partial-update requirements justify it.

8.6 Entity

Modify:

recruitdirect-domain/src/main/java/com/recruitdirect/model/entity/Job.java

Add:

@Column(name = "resume_process_limit")
private Integer resumeProcessLimit;

@Column(name = "interview_limit")
private Integer interviewLimit;

@Column(name = "resume_process_model", length = 128)
private String resumeProcessModel;

@Column(name = "interview_model", length = 128)
private String interviewModel;

Use Integer, not primitive int, so existing jobs can remain unconfigured after migration.

9. Database Design

9.1 Recommended approach

Add four nullable columns to the existing job table.

Rationale:

The values are scoped one-to-one to a Job.

Job already stores other job-level operational configuration.

No history, versioning, or multiple configuration profiles are required.

A separate one-to-one table would add a join, repository, entity relationship, and migration complexity without a current functional benefit.

Existing Job retrieval and persistence can be reused.

9.2 Proposed schema

ALTER TABLE job
    ADD COLUMN resume_process_limit INT NULL,
    ADD COLUMN interview_limit INT NULL,
    ADD COLUMN resume_process_model VARCHAR(128) NULL,
    ADD COLUMN interview_model VARCHAR(128) NULL;

9.3 Existing rows

All existing jobs receive NULL for the four fields.

NULL means:

No job-specific value has been configured.

The runtime meaning of NULL must be confirmed:

Use an application/system default, or

Treat it as configuration missing.

The admin UI will display null numeric values as empty fields and null model values as empty text.

9.4 Rollback SQL

ALTER TABLE job
    DROP COLUMN resume_process_limit,
    DROP COLUMN interview_limit,
    DROP COLUMN resume_process_model,
    DROP COLUMN interview_model;

9.5 Migration file

Create a new migration file following the repository's existing SQL-migration convention, for example:

migration_add_job_processing_configuration.sql

The exact naming/version convention should match Jian's preferred database deployment process.

10. Request Flows

10.1 Load flow

Admin opens Job Configuration page
    -> enters Job UUID
    -> frontend validates non-empty input
    -> GET /job/admin/configuration/{jobId}
    -> Axios interceptor attaches Firebase token
    -> FirebaseAuthInterceptor verifies token
    -> backend resolves HiringClient
    -> backend checks role == admin
    -> JobService loads Job
    -> controller returns job summary + configuration
    -> frontend populates read-only summary and editable fields

10.2 Save flow

Admin edits configuration
    -> frontend validates fields
    -> PUT /job/admin/configuration/{jobId}
    -> backend authenticates and authorizes admin
    -> backend validates values
    -> JobService updates entity in one transaction
    -> repository saves Job
    -> backend returns persisted configuration
    -> frontend replaces local baseline
    -> frontend shows success notification

12. Validation and Error Handling

12.1 Frontend validation

Job ID cannot be blank.

Limits must be integers greater than zero when provided.

Model names are trimmed.

Model names cannot be whitespace-only.

Save is disabled while loading or saving.

Save is disabled when no changes exist.

API validation errors remain visible without clearing the form.

12.2 Backend validation

Backend validation is authoritative.

Reject malformed Job IDs with 400.

Reject zero or negative limits with 400.

Normalize empty model strings to null.

Reject model names longer than 128 characters.

Return 404 for unknown Job ID.

Return 403 for non-admin users.

Avoid returning stack traces or internal SQL errors to the frontend.

12.3 Logging

Log:

Admin identity

Job ID

Whether the request was load or update

Success/failure

Validation and authorization failures

Do not log:

Firebase ID tokens

Full Authorization headers

Secrets

Sensitive resume or interview data

15. Risks and Mitigations

Risk 1: Frontend admin role can be modified in local storage

Mitigation: Frontend role checks are only for navigation and user experience. Backend authorization always uses the authenticated Firebase identity and database-backed HiringClient role.

Risk 2: Existing jobs have no configuration values

Mitigation: Use nullable database fields and clearly define null behavior before runtime integration.

Risk 3: Model names are not standardized

Mitigation: Start with validated text fields. Change to dropdowns after the supported model list is confirmed.

Risk 4: Job ID may mean UUID or short ID

Mitigation: Initial implementation uses the existing Job UUID. Confirm whether administrators also need short_id lookup before development.

Risk 5: Configuration is stored but not consumed

Mitigation: Explicitly separate configuration management from runtime integration. Add runtime consumers only after ownership and expected behavior are confirmed.

Risk 6: Admin checks are duplicated

Mitigation: Add or reuse a centralized requireAdmin helper in the HiringClient service layer.
